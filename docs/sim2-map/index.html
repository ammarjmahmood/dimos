THE RUNNING SYSTEM

Two loops move the robot.
Three more let DimOS observe it.

One loop decides what the motors should do. Another applies those commands and advances the world. Feedback, camera and lidar run alongside them, on their own clocks.

The controller does not wait for an image or a lidar scan before keeping the robot balanced.

Meanwhile, the same world feeds:robot feedback 200 Hzcamera 10 Hzlidar 10 Hz
01

THE CONTROL LOOP · EXISTING DIMOS

Choose what every motor should do.

50 Hz
every 20 ms

Suppose a person presses forward, or navigation asks the robot to walk forward. That changes a desired velocity. It does not directly set a leg angle or step the simulator.

  1. Read the latest measured state.The coordinator's hardware adapter reads joint positions and velocities from shared memory. Its IMU reading comes from that same sampled frame.
  2. Run the active control tasks.The GR00T policy turns state and desired velocity into targets for the legs and waist. An arm trajectory task can supply other joint targets.
  3. Resolve competing commands, then write.The coordinator chooses the winning command for each joint. Its adapter writes targets, gains and feedforward effort to the robot's shared-memory channel.

The actual machinery

ControlCoordinator owns a TickLoop thread. That calls ordinary task and hardware objects. WholeBodyAdapter translates the existing hardware API into shared-memory reads and writes; it has no control thread of its own.

At the end of this tick, the simulator has a new target available. The coordinator sleeps until its next tick.

Follow this loop in the code

TickLoop._tick() → task.compute() → ConnectedWholeBody.write_joint_commands() → WholeBodyAdapter.write_motor_commands()

02

THE PHYSICS LOOP · SIM2

Apply the targets. Move the world.

200 Hz
every 5 ms

This loop keeps running between policy decisions. In the current G1 configuration, the intended ratio is four physics steps for each controller tick.

  1. Read the latest target for each robot.The input is the shared-memory action frame, not an RPC request. If the controller has not written another target, physics reuses the previous one.
  2. Apply the motor model and call MuJoCo.For G1, target error and gains produce actuator torque. mj_step() advances contacts, joints and the rest of the scene. This is the only owner that advances physical time.
  3. Publish what actually happened.Joint and IMU observations go back to each robot's channel every physics step. A separate shared-memory snapshot holds the world state for cameras, lidar and the optional viewer.

The actual machinery

SimulationModule._run() is a timer thread in the physics worker. It calls SimulationRuntime.step(), which owns the authoritative MjModel and MjData, a lock, and the robot channels. Motor PD is computed inside this loop, not in another module or thread.

Why two shared-memory payloads?

Motor feedback is small and robot-specific: joints, IMU and root pose. The world snapshot includes the state needed to reconstruct the whole scene. Sending the full scene state through every motor read would waste work.

Both reuse RobotChannel's frame machinery. They are data channels, not two physics engines. Snapshot publication is scheduled inside the physics loop, nominally near 60 Hz, rounded to whole physics steps.

Follow this loop in the code

SimulationModule._run() → SimulationRuntime.step() → _apply() → mj_step() → _publish()

THE INNER LOOP IS NOW CLOSED

The next controller tick reads those new joints and IMU values. That is enough to run the locomotion policy. The remaining loops make the robot useful to the rest of DimOS.

03

THE FEEDBACK-PUBLISHING LOOP · SIM2

Make robot state available as normal DimOS messages.

200 Hz
G1 IMU configuration

The control loop reads state synchronously through a hardware API. Navigation, visualization and other modules consume messages instead. This loop serves that second audience.

  1. Sample the robot channel.WholeBodyConnection uses its own adapter instance to read the latest measured joints, IMU and root pose.
  2. Publish typed streams.motor_states: JointState, imu: Imu, odom: PoseStamped and tf: TFMessage enter the configured DimOS transport, such as Zenoh.

The actual machinery

WholeBodyConnection._publish() is one publisher thread. It does not run a policy or own physics. Its adapter is a second instance of the same class used by the coordinator, attached to the same robot channel.

A real duplication question: the coordinator also publishes joint-state streams. This connection additionally publishes IMU, pose and TF. Two publication paths exist today; that cost should be justified, not disguised as an architectural necessity.

This simulated odom is ground truth. It is not a localization estimate produced by SLAM.

04

TWO SENSOR LOOPS · SIM2

Make an image. Cast a scan.

10 Hz each
every 100 ms

The camera and lidar are independent workers. They use the same scheduling and world-reading machinery, but different measurement algorithms.

  1. Read a fresh world snapshot.WorldReader restores saved state into its worker-local MuJoCo model and data. mj_forward() recomputes positions; it does not advance physical time. An already-seen snapshot is skipped.
  2. Measure from the robot's mounted sensor.The camera renders RGB and depth from its named MJCF camera. The lidar transforms its configured rays through its named MJCF site and raycasts the scene.
  3. Publish the measurement.Camera images, calibration and transforms use the captured snapshot's time. Lidar publishes a PointCloud2, with a transform when using sensor-frame output.
CAMERA

SensorModule._run() → WorldReader.update() → MujocoCamera.capture() → images

LIDAR

SensorModule._run() → WorldReader.update() → Raycaster.cast() → point cloud

The actual machinery

Each sensor module requests a dedicated worker and runs a capture thread. Each WorldReader loads the prepared model once, then copies state each capture. A camera owns its renderer; a lidar owns its ray pattern and raycaster. These helper objects are not more DimOS modules.

The cost of independence: each sensor owns a model/data copy and repeats state reconstruction. It avoids waiting for rendering inside the physics loop, but it still competes for CPU, memory bandwidth and GPU resources.

What happens when a sensor is slow?

The capture loop finishes its current work, then reads the newest available snapshot. It does not accumulate a mandatory queue of every physics frame. Its achieved rate can fall below 10 Hz. There is no direct camera-completion barrier in the physics loop.

The lidar here is an ideal instantaneous scan, not time-resolved Mid360 hardware emulation. No separate IMU worker is needed: MuJoCo samples the IMU with the joint observation in the physics owner.

THE LARGER BEHAVIOR LOOP · EXISTING DIMOS

Use what the robot sees to choose the next command.

A locomotion policy keeps moving toward a requested velocity. Navigation decides which velocity is useful. That is a larger feedback loop built from existing modules, not another subsystem inside sim2.

  1. Build a map from lidar.The current G1 sim blueprint feeds VoxelGridMapper, then CostMapper.
  2. Plan using the map, goal and robot pose.ReplanningAStarPlanner produces navigation velocity commands. MovementManager selects between navigation and teleoperation.
  3. Return to the control loop.The resulting cmd_vel: Twist reaches the coordinator and updates the task's desired velocity. The next 50 Hz control tick turns it into motor targets.

The outer loop asks, "Where should I go?" The inner loop keeps answering, "What should my motors do now?"

The map and planner have their own callbacks and scheduling. They are not all executed in one 50 Hz tick. Camera output can feed visualization or perception; GR00T locomotion in this blueprint does not consume RGB-D.

ONCE, BEFORE THE LOOPS

Where the modules, robots and sensors come from.

  1. The robot definition describes the device.G1_GROOT names the MJCF, joints, actuator mappings, initial pose and sensors. A named camera or site supplies the physical mount.
  2. The existing blueprint composes it.simulation(scene=..., robots=...) returns .blueprint and .hardware. The first declares simulation/device modules; the second tells the existing coordinator how to attach its adapter.
  3. The world is built, then the loops start.SimulationModule.build() composes the model, creates the shared-memory channels and writes a temporary compiled world.mjb. Sensor workers get its path and snapshot descriptor through describe(), then load their local copies.

For G1, sim2 adds four modules: one world, one robot-feedback connection, one camera and one lidar. The coordinator is an existing DimOS module. An adapter, a snapshot and a robot definition are not deployable modules.

Where do RPCs, reset and the two viewers fit?

RPCs handle lifecycle and occasional commands such as describe(), reset(), set_spawn() and set_scene_state(). They are not the per-tick motor data path. Physics mutations share the runtime lock; resetting physics does not, by itself, clear every controller or mapper's history.

The optional native MuJoCo viewer owns another WorldReader. It refreshes a read-only view, with a 1/30-second sleep between iterations. Rerun instead subscribes to DimOS messages. Neither window advances physics.

An optional privileged sim_truth publisher runs at 10 Hz when enabled for evaluation recording. It is not required for locomotion, sensing or navigation.

THE ARCHITECTURE, NOW IN CONTEXT

Which boundaries earn their place?

Control separate from physics
DimOS owns policies and command arbitration; the emulator owns motors and physical state. The same control code can target hardware. It also introduces asynchronous timing and a transport contract to maintain.
Sensors separate from physics
Slow rendering does not sit inside the stepping loop. The price is per-sensor model copies and repeated mj_forward(). Sharing reconstruction is a possible optimization, not something this implementation already does.
Feedback publication separate from control
It gives ordinary DimOS consumers the device streams they expect. It also means a second adapter and overlapping joint-state publication. This is the clearest place to question consolidation.
Shared memory in the motor path
It serves synchronous hardware methods without a network RPC per tick. The binary frame layout, reset identity and lifecycle handling are real maintenance costs. This is the current choice, not proof that measured Zenoh performance could never replace it.
Latest-value reads instead of lockstep
Loops can run at different rates. They can also see stale values. Physics reuses the last valid target; _apply() checks episode identity but has no elapsed-time stale-target watchdog. A task's velocity-command timeout is a different safeguard.

That is the architecture to judge: two independently scheduled control/physics loops, separate observation loops, and ordinary DimOS modules closing the larger behavior loop.

What changes for M20 or xArm7?

M20: the same loop structure, a different policy, 50 Hz controller and 1,000 Hz physics. Wheel velocity targets and leg position targets use the same full motor command contract.

xArm7: trajectory/gripper tasks replace locomotion, the default coordinator tick is 100 Hz, and physics is 200 Hz. The arm uses its native position-servo actuators. ManipulatorConnection publishes joint feedback at 50 Hz; the wrist camera runs at 10 Hz. This configuration has no lidar or whole-body IMU loop.
